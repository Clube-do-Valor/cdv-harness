# cdv-harness

The house agent harness: the workflow skills, rules and instructions that a team's repositories share, kept in one place and copied (vendored) into each repository that uses them.

It carries process only. Every fact of a repository — its commands, paths, PR host, ticket system, integrations and domain — lives in that repository, in its profile and its extensions, never here.

## Layout

```
skills/cdv-*/            the house skills (SKILL.md + references/ + scripts/)
rules/core/*.md          house path rules; `{app_dir}` in `paths:` is rewritten by sync
instructions/house.md    the house block written into the repository's instructions file
settings/deny-core.json  permission deny rules merged into .claude/settings.json
profile.schema.yaml      the variables a repository declares in its profile
bin/harness              the tool: sync, verify, propose, catalog, release, lint, scan
bin/verify.sh            the offline CI gate, vendored into each repository
CATALOG.md, registry.json  generated by `bin/harness catalog`
```

## In a consumer repository

```
.claude/skills/cdv-*/              vendored, pinned by the lock
.claude/rules/core/                vendored
.claude/harness/bin/verify.sh      vendored
.claude/harness.lock               source, tag, commit, tree_sha256, paths, files
.claude/harness/profile.yaml       the repository's facts (committed)
.claude/harness/profile.local.yaml the machine's facts (ignored by git)
<extension_dir>/cdv-<skill>.md     optional extension of one skill: adds or restricts, never repeats
```

Every core skill reads the profile in its step 0 and stops when it is missing, then reads its extension when there is one. Skills that exist only in one repository keep their own names and are referenced from the core through profile keys (`design_skill`, `module_design_skill`…).

## Adopt it

1. Write `.claude/harness/profile.yaml` from `profile.schema.yaml` (`harness_source` is the git URL of this repository).
2. Run `bin/harness sync <tag> --from <checkout of this repository> --repo <consumer>` (without `--from`, it clones `harness_source`). It copies the skills, rules and gate, merges the deny list, writes the house block between `<!-- cdv-harness:house vX.Y.Z -->` markers, removes what an older tag shipped and this one does not, writes the lock and stages everything with `git add -f` (a repository may ignore `.claude/`). `--pr` also commits, pushes `chore/harness-sync-<tag>` and opens the PR through the profile's `pr_cli` (`gh` or the bundled Bitbucket client).
3. Add the gate to the repository's CI on pull requests: `sh .claude/harness/bin/verify.sh`. It needs no network: it recomputes the hash of the vendored files and compares it with the lock. Exit 0 matches, 1 lists the changed, created and deleted files, 2 means the lock is missing or invalid.

`bin/harness sync --user <tag>` installs `cdv-grilling`, `cdv-grill-me` and `cdv-research-round` as copies into `~/.claude/skills/`, with `~/.claude/harness-user.lock`, for work outside any repository. It refuses to replace a skill it did not install.

## Upstream first

The vendored copy is never edited in place: the gate fails the PR, and the core deny list blocks the agent's Edit tool on those paths. A change goes here first:

- `bin/harness propose --from <checkout of this repository>` (run in the consumer) takes what diverged from the lock back to the core paths on a `propose/<date>-<label>` branch and opens the PR. The branch, commit and PR never name the consumer (the label is random). Before anything is written, the proposed files and their paths go through `scan` with the core's patterns plus the private ones (`--extra-patterns`, default `~/.config/cdv-harness/private-patterns.txt`; without them it stops unless `--public-patterns-only` is given), and so does the git identity that would sign the commit: one finding and nothing is proposed. `release` checks the identity of its tag the same way. `{app_dir}` is restored in the rules, and the house block goes back to `instructions/house.md`.
- After the merge, a tag, and `sync` brings it to each repository.
- An emergency commit in a consumer may carry `Harness-skip: <reason>`; `verify.sh --skip-trailer-range <base>..HEAD` then passes and prints the reason for the reviewer.

## Releases

`bin/harness release` tags at most once a week and only when `main` changed since the last tag: minor when a `feat` commit landed, patch otherwise. Then it runs `sync --pr` in each consumer listed in a machine-local `~/.config/cdv-harness/consumers.yaml`. With no change, or with a tag younger than 7 days, it does nothing. `--dry-run` prints the decision. Nothing schedules it yet: it runs by hand.

## Gates of this repository

```
python3 -m unittest discover -s tests -v
bin/harness lint                 # name = folder, kebab-case, ≤ 64; description ≤ 1024; strict YAML; metadata.version and owner
bin/harness scan --commits HEAD  # files, paths, commit identities and messages, tags; add --extra-patterns <file> for the private patterns kept outside the repository
bin/harness catalog --check      # CATALOG.md and registry.json are up to date
```

CI runs all of them on every pull request. `scan` is the publication barrier: this repository is public, so a company fact, an internal hostname, a person's name, a ticket key or a token never lands here. `scan-allowlist.txt` lists the motivated exceptions.

The tool needs Python 3.10 or newer and nothing outside the standard library; `verify.sh` needs only POSIX `sh`, `find`, `sort`, `sed`, `awk` and `sha256sum`.
