# What the API cannot do, and what to do instead

The public REST API covers almost everything the Notion MCP did, but not all of it. When a request needs one of these, say so and do the alternative; never pretend it happened. Sources: the official reference at https://developers.notion.com (comments, search, users, request limits), as read on 2026-11-22.

| The API cannot | Do instead |
|---|---|
| Read resolved comments: `GET /v1/comments` returns only open discussions | Say that resolved threads are not visible to the integration; ask the user to paste what matters from them, or reopen the thread in Notion |
| Resolve a discussion, or reopen one | Ask the user to resolve it in Notion; a reply (`notion comments reply`) can say it is settled |
| Start a discussion anchored to a selected text | Comment on the page (`notion comments add`) quoting the passage, or reply to an existing thread |
| Search page bodies: `POST /v1/search` matches titles only, and also returns titles that only resemble the words (printed `matched: similar title`) | `notion search` also looks in each connected data source's title and text properties; for the body, narrow with `notion query`, then `notion fetch` the candidates and read them |
| Edit or delete another author's comment: a token edits only its own comments | Reply in the same discussion with the correction (`notion comments reply <discussion>`) |
| Keep the person as the author: page authorship and every edit show the integration | Fill `Requester` / `Assignee`-style properties explicitly, and sign comments (`me` in the settings); the history stays the integration's |
| List guests in `GET /v1/users` | `notion users find` also knows everyone seen in person properties of rows already read; pass `user://<uuid>` when you have it |
| Run SQL, joins or aggregates over data sources | `notion query --where … --count` / `--group-by`; a join is two queries and a match on the relation ids in the shell |
| Filter on formulas or rollups through `--where` | `notion api POST /v1/data_sources/<id>/query --data '<filter json>'` with the formula/rollup filter |
| Duplicate a page | `notion create` with the fetched properties and body, or a template through `notion api` |
| Restore page history or see past versions | Ask the user to use the page history in Notion |
| Create folders, or AI search | Not available to integrations |

## Limits a command can meet

- **Rate:** a fixed 60-second window per integration (about 3 requests a second on most plans, 10 on Business and Enterprise) plus a workspace budget shared by every integration. The client waits out each 429 (`Retry-After`, at most 5 times); a shared token means teammates share the window, so prefer one `--count` to many fetches.
- **Writes in doubt:** a write that fails is one of three cases, and the client says which. Refused: Notion answered a 4xx (a 429 once its retries are used up), and nothing changed. Not sent: the connection could not be made (name resolution, a refused connection, no route, the TLS handshake), so the request never left the machine and nothing changed. In doubt: the request left and no answer says what happened (any 5xx, a timeout, a connection reset, closed or broken by a TLS error after the request left, a redirect, or a 200 whose body is not the API's JSON, such as a proxy's page), so it may have been applied. The client never resends a write in doubt; fetch the page and check it before running that part again. After a create in doubt the client looks for a page with that title made by this integration since the minute the command started; when it finds none, or cannot look (the search fails, times out or keeps answering 429), the create stays in doubt, so look for a page with that title in that parent before creating it again. On the search: Notion stores `created_time` to the minute, so a page with the same title made earlier in that minute (another run, a teammate on the same token) looks the same. Read the page found (`notion fetch <url>`) before treating it as the new one, and avoid creating two pages with one title in the same minute.
- **Sizes:** 2,000 characters per rich text piece (the client splits titles and text) and per link address, 100 pieces per title or text value (a value with 60 links is about 120 pieces, and Notion refuses it with a 400: shorten it or put the links in the body), 100 items per people, relation or multi-select write, 100 edits per `--edit` call, about 5,000 blocks per body write and about 20,000 per read (a longer page reads back with `<unknown>` markers and `truncated`).
- **Formatting inside a text property:** links are read and written as `[text](url)`; other formatting (bold, italic, code, colour, mentions, equations) is read as plain text and is lost when the property is rewritten with `--set`. A page body keeps all of it.
- **Page comments share one discussion:** `notion comments add` on a page that already has an open page-level discussion joins it, so a second `add` reads as a reply. An edited comment keeps the name it was signed with. A comment's text is printed the way a text property is ([properties-and-filters.md](properties-and-filters.md)): a link as `[text](url)`, everything else as plain text.
- **Nesting:** filter groups two levels deep.
- **Query results:** 10,000 rows per query on Notion's side; the client stops at 2,000 unless `--max-rows` raises it.
- **Files:** one upload takes up to 20 MB and must be attached within an hour. A body takes an uploaded file only through the line `notion upload` prints (the client places it, see [notion-markdown.md](notion-markdown.md)); a comment does not. Signed download urls (the file host is Notion's own storage, never `api.notion.com`) expire after an hour: fetch the page again for fresh ones. A files property prints its file names; the urls are in `notion fetch <ref> --json`.
- **Access:** the integration sees only the pages and data sources connected to it (inherited by their children). A 404 or 403 on a page that exists means it is not connected: the message names the id; a person with access adds the integration through the page menu → Connections.
