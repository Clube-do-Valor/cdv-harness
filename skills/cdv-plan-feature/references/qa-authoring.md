# QA authoring rules — Step 4c (full doctrine)

Load when Step 4c begins. These rules govern how the feature-specific sections of `QA-<slug>.md` are composed. Every command uses the container prefix (`profile.cmd_container_exec`) when `profile.commands_run_on` is `container`, and includes an `**Expected:**` block. The extension (`<profile.extension_dir>/cdv-plan-feature.md`, heading "QA authoring") adds the repository's scope traps and real cases.

- **Expected values must be real-data-derived (mandatory).** The local app DB is `profile.qa_env` and reading it is DEV-SAFE (Step 3.5). Before writing the `**Expected:**` blocks, run read-only queries to (a) pick the *richest real fixture* for the feature's scope — the owner/record that actually exercises every field and edge — and (b) compute the concrete expected numbers, then bake **real ids + counts** into the steps. Abstract expectations are unfalsifiable: they "pass" even when the feature renders all-stub, empty, or the wrong scope.

  > ❌ **BAD** (vibe check — an all-stub list would have passed it): *"open the screen as an owner → expect their records with all fields."*
  > ✅ **GOOD** (real fixture pre-queried from the DB): *"`/<screen>?owner=<id>` (a named owner) → **42** records, **17** with field A, **9** with field B; sparsity is expected, and identical name across ids ⇒ stub leak."*

  Keep PII out of the committed `QA-<slug>.md`: prefer opaque ids and counts; if a step needs identifying values, write them to a gitignored scratch file and reference its path, never inline.
- **A fixture is named by what the surface consumes (hard rule).** An id identifies a row; it does not help a tester who has to *find* the entity. Any step where the tester locates the fixture through a UI affordance — a search box, a dropdown, an autocomplete, a table filter — must carry the **label that surface displays** (the person's name, the client's name, the role's name), because an id cannot be typed into a name search. Ids belong where they are actually consumed: URLs, query params, REPL probes, `**Expected:**` blocks. **Derive and write both**: `user 15 (Jane Doe)` — never the id alone. Cheap tell: if a step says "pick user 15" and the screen has no id column, the step is un-runnable as written. (e.g. a guide that names a form's users by id leaves the tester unable to find them in the picker.)
- **No placeholder entity ids (hard rule).** Every browser/staging/REPL step must name a **real** id pre-queried from the DB — never `{your-client-id}`, `<id>`, `SOME_ID`, `{some-client}`, or prose like "pick one of your own clients." A placeholder id is the same unfalsifiable failure as an abstract `**Expected:**`: the step "passes" by being un-runnable. The ONLY literal braces allowed in the emitted QA are framework route patterns echoed verbatim by `route:list` (e.g. an `items/{item}/edit` row in a route-table check). The mechanical check runs in the Step 4c lint gate.
- **Local environment only — never the production domain (hard rule).** QA is executed locally against `profile.qa_env`, so every browser/URL step targets the local host (`profile.qa_url`), NEVER a production host. A production URL risks a tester mutating real data — and turns a `[PRODUCTION-AFFECTING]` step into an actual prod write. Write URLs as `<profile.qa_url>/<route>/<real-id>/…` — the host check runs in the Step 4c lint gate.
- **External-sourced or owner-scoped screens still get a real fixture — placeholders are never the fallback.** When the rendered values come from an external system and are not in the local DB, or the screen is owner-scoped so "it depends who's logged in," do NOT retreat to a placeholder. Derive all of these from the QA database (`profile.qa_env`, DEV-SAFE):
  1. **A real entity id, derived from the feature's ACTUAL scope source — not a look-alike table.** Read the guard/controller to find the exact method that defines "in scope" (the guard, then the service method it calls, then the cached lookup behind it), then derive the fixture by calling THAT method in a read-only REPL probe and picking an id it actually returns. Do **not** substitute a plausible proxy like an owner column on the entity table — it can diverge from the real scope (wrong count, or an id that 404s). Then **reproduce the guard end-to-end** in the probe (does the chosen id pass the guard's membership check for the chosen scope?) so you know the URL yields 200, not 404, before baking it in.
  2. **Verify the scope (acting-as) parameter's REAL identifier — its name can lie.** Trace how the param is consumed, not what it's called: a parameter named after one identifier may be matched by the code against another, and passing the identifier its name suggests silently falls back to the caller's own scope and 404s. Bake the identifier the code actually matches on, and note the distinction in the step. Where the scope is carried by a cookie or session instead of the query string, the step must first perform the action that sets it, then open the deep URL with no scope parameter — a scope query parameter appended to a deep link that does not read it is a silent no-op.
  3. **Local-derivable counts / sparsity** for the `**Expected:**` block, computed from the SAME source as the scope (e.g. "the owner scopes N contacts; only M have a birthdate → an empty field is the expected common case"). If your count came from a different query than the guard uses, that mismatch is the tell that you derived from the wrong source — reconcile before baking.
  4. **A gitignored scratch oracle** for the external/PII values: a REPL one-liner that writes the per-entity expected values to `storage/app/qa-scratch/<slug>-<id>.json` (gitignored) and **echoes only the path**, with the step instructing the tester to read the scratch file and cross-check external-only fields against the source UI. Recipe:
     ```bash
     <profile.cmd_tinker>='$r=\App\Models\Record::where("external_id","<REAL_ID>")->first(); @mkdir(storage_path("app/qa-scratch")); file_put_contents(storage_path("app/qa-scratch/<slug>-<REAL_ID>.json"), json_encode(["name"=>$r->name,"email"=>$r->email], JSON_PRETTY_PRINT|JSON_UNESCAPED_UNICODE)); echo "wrote ".storage_path("app/qa-scratch/<slug>-<REAL_ID>.json");'
     ```
     Note in the step which fields are external-only (live in the source system, not the QA database) so the tester knows the scratch file is a partial oracle and the source UI is authoritative for the rest.
- **Test runner:** use `profile.cmd_test_backend` and nothing else — a QA guide never names a second runner, even when the framework registers one (`php artisan test` exists under Collision, but the repository's single runner is the binary CI executes), so QA guides name it directly: `<profile.cmd_container_exec> <profile.cmd_test_backend> --filter=<FILTER>` (the filter form is `profile.cmd_test_backend_filter`).
- **REPL commands:** ALL REPL-based steps MUST use the single-line `--execute` form (`profile.cmd_tinker`). Heredoc (`<<'EOF' ... EOF`) is FORBIDDEN — it breaks silently when copied from rendered markdown because indentation or the closing fence gets included.

  ❌ BAD — heredoc breaks on copy-paste from markdown:
  ```bash
  php artisan tinker --no-interaction <<'EOF'
  use App\Models\Foo;
  $f = Foo::first();
  print_r($f->toArray());
  EOF
  ```

  ✅ GOOD — single-line, copy-paste safe:
  ```bash
  <profile.cmd_tinker>="use App\Models\Foo; \$f = Foo::first(); print_r(\$f->toArray());"
  ```

  Escaping rules inside `--execute="..."`: variables use `\$var`; string literals use single quotes; backslash namespaces (e.g. `App\Models\Foo`) need no escaping.

- **Mutation labels:** Every section heading must carry one of: `` `[READ-ONLY]` `` (reads only — includes running the test suite, static analysis, and DB reads against the local app DB), `` `[MUTABLE: <what it writes>]` `` (manually creates, updates, or deletes rows in the local app DB, or triggers a service that does so, with NO external/production side-effect), or `` `[PRODUCTION-AFFECTING: <what it touches>]` `` (writes to or mutates an external system shared with prod — any of `profile.production_writing_integrations`, any Slack/email/SMS reaching a real person — or dispatches a job that does so; per Step 3.5. Reading real data is not production-affecting). Do NOT label automated test suites as MUTABLE — the database-refresh trait is a framework mechanism, not a developer-visible side-effect.
- **PRODUCTION-AFFECTING steps are manual-only.** They are never auto-run by the agent, and the QA header must carry the `important: do not run the [PRODUCTION-AFFECTING] steps yourself` note from Step 3.7.
- The preamble must include a one-line legend explaining the three labels.
- **Inertia page availability (backend slices that render a Vue page authored on another branch).** When a controller in this slice does `Inertia::render('Some/Page', …)`, check the component exists on this branch before writing any browser step: `find <profile.app_dir>/<profile.frontend_root> -ipath '*<Module>*' -name '<Page>.vue'`. If it is absent, the route resolves but Inertia throws `Page not found: Some/Page` client-side. **Default fix: bundle the screen's page into the slice** — copy it (and its spec) **unmodified** from the authoring branch (`git checkout <front-ref> -- <page-path> <spec-path>`), so the screen renders against the real controller on this branch and is browser-QA-able without an integration branch; the extension names the repository decision that sets this default or restricts it. "Frontend untouched" means *not modified*, not *not present*; bundling a verbatim page is the default, and identical content reconciles as a no-op at merge. **Verify it actually RENDERS, not just builds:** the frontend spec + the frontend build (`profile.cmd_build_frontend`, when the repository has one) are necessary but not sufficient — bundling exercises the page against the real controller for the first time and can surface a latent bug the frontend-only PR never hit (e.g. a page that omits a prop its layout needs can throw at mount, though its spec is green and its build clean). When the page does not render, apply the **minimal** fix to match the sibling pages' contract, note it as the sanctioned deviation from verbatim, and **flag the same fix to the authoring branch**. Only if bundling is genuinely impossible, fall back to a precondition naming the owning branch + the integration/staging path. Never present a browser step as runnable on a branch that lacks its page.
